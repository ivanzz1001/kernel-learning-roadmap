# 第 3 章：内核模块、字符设备与设备模型

## 本章目标

完成一个可被用户程序访问的字符设备，具备并发安全、阻塞/非阻塞 I/O、`poll`、统计信息、错误处理和自动化回归测试。

## 第 9 周：模块基础

### 最小模块骨架

```c
#include <linux/init.h>
#include <linux/module.h>

static char *label = "lab";
module_param(label, charp, 0444);
MODULE_PARM_DESC(label, "Label printed by the lab module");

static int __init lab_init(void)
{
    pr_info("lab: loaded label=%s\n", label);
    return 0;
}

static void __exit lab_exit(void)
{
    pr_info("lab: unloaded\n");
}

module_init(lab_init);
module_exit(lab_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Kernel learning lab module");
```

外部模块 Makefile：

```make
obj-m += lab.o

KDIR ?= ../build

all:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules

clean:
	$(MAKE) -C $(KDIR) M=$(CURDIR) clean
```

学习任务：预处理或展开宏，说明 `module_init`、`__init`、module metadata 最终如何进入产物。用 `modinfo`、`nm`、`readelf` 观察 `.ko`。

### 加载生命周期

```bash
insmod lab.ko label=test
lsmod
cat /sys/module/lab/parameters/label
dmesg | tail
rmmod lab
```

不要在宿主机加载未经验证的学习模块。把 `.ko` 放进 initramfs 或通过只读共享方式传入客体。版本、配置或编译器不匹配时先检查 vermagic。

## 第 10 周：字符设备数据路径

### 对象关系

```text
用户 fd
  → struct file
  → file_operations
  → 驱动私有对象
  → 缓冲区/硬件状态
```

关键问题：

- `open` 怎样找到设备对象？
- 私有状态属于全设备、每次 open 还是每次请求？
- 文件偏移由谁维护？
- 用户缓冲区为什么不能直接解引用？
- 设备被删除时，仍打开的 fd 怎么办？

### 实现顺序

1. 动态分配设备号：`alloc_chrdev_region`。
2. 初始化和注册 `cdev`。
3. 建立 class/device，触发 `/dev` 节点创建。
4. 实现 open/release。
5. 加入固定大小缓冲区的 read/write。
6. 使用 `copy_to_user`/`copy_from_user` 并正确处理未复制字节。
7. 逐步加入 ioctl、阻塞读和 poll。

每一步都要能单独加载、测试、卸载；初始化失败使用逆序清理或合适的资源管理方法。

### read/write 语义检查

- `count == 0` 应如何处理？
- 缓冲区不足是部分写、阻塞还是 `-ENOSPC`？契约必须明确。
- nonblocking fd 没有数据时返回什么？
- 信号打断等待时返回什么？
- read 到 EOF 的语义是否适用于你的设备？
- `copy_*_user` 返回值不是普通负 errno；必须查 API 契约。

## 第 11 周：wait queue 与 poll

### 状态机先于代码

先写状态机：

```text
EMPTY --write--> READABLE --read-all--> EMPTY
  │                 │
  └─ nonblock: EAGAIN
  └─ blocking: sleep on readq
```

写入改变条件后：在保护状态的锁内完成状态更新，再唤醒等待者。等待条件必须能在持锁或合适同步下重新检查，以处理虚假唤醒和竞争。

### poll 实验

用户态同时创建：

- 一个阻塞 reader；
- 一个 `O_NONBLOCK` reader；
- 一个使用 `poll()` 等待可读/可写事件的 reader；
- 多个并发 writer。

记录各自预期返回值、唤醒次数、数据完整性。使用超时避免错误实现把测试永久挂住。

## 第 12 周：并发、生命周期和错误路径

### 锁设计表

为每个字段明确：

| 字段 | 所有者 | 访问上下文 | 保护方式 | 生命周期结束条件 |
|---|---|---|---|---|
| buffer |  |  |  |  |
| length |  |  |  |  |
| open_count |  |  |  |  |
| device state |  |  |  |  |

如果所有访问都发生在进程上下文且可能睡眠，mutex 往往比 spinlock 更自然。选择锁不是性能猜测，而是由上下文、临界区和睡眠要求决定。

### 压力测试

至少运行：

- 8 个 writer + 8 个 reader，持续 60 秒；
- 随机长度，包括 0、1、边界值、超长输入；
- 随机发送 signal；
- 测试期间反复 open/close；
- 模块装卸 100 次（确保没有打开 fd）；
- KASAN/lockdep 配置下重复。

### 失败注入

为初始化的每个资源申请点设计失败情形。可以使用内核 fault injection，也可先用模块参数在第 N 步主动返回错误。验收标准是：加载失败无泄漏、无残留设备节点、后续可以成功加载。

## 第 13 周：设备模型与 sysfs

### 设备模型地图

- **bus**：设备和驱动匹配发生的逻辑场所。
- **device**：内核中的设备实例和生命周期对象。
- **driver**：支持某类设备的实现。
- **class**：面向用户空间的功能分类。
- **sysfs**：kobject 层级和属性的用户可见投影，不是任意调试数据仓库。

### sysfs 属性要求

- 一个文件表达一个清晰属性。
- 文本格式稳定、可解释，写入必须验证范围与格式。
- show/store 处理并发和设备删除。
- 不泄漏指针、内核地址或敏感数据。
- 调试数据优先考虑 debugfs，稳定配置接口再考虑 sysfs。

### platform driver 实验

不依赖真实硬件时，可以通过模块或设备树创建一个受控 platform device，再编写匹配 driver。记录 probe/remove 的触发顺序、devm 管理资源的释放时机和绑定状态。

## 阶段项目：counter/queue 字符设备

### 必备功能

- 多实例设备，每个实例有独立状态。
- read/write 与清晰的容量策略。
- blocking/nonblocking 行为。
- `poll()`。
- 一个版本化 ioctl 或用 read/write/sysfs 替代并解释选择。
- sysfs 只读统计：读写次数、等待者、丢弃数。
- 模块卸载前正确处理设备注册和打开引用。
- 用户态回归程序与 shell 测试入口。

### 评审清单

- [ ] 所有用户指针均通过 uaccess API。
- [ ] size/offset 运算检查溢出、负值和边界。
- [ ] 初始化失败逆序释放完整。
- [ ] 锁覆盖状态与不变量，而不只是覆盖某行代码。
- [ ] 等待条件在循环中重新判断。
- [ ] 没有在持 spinlock 时睡眠或访问用户内存。
- [ ] unload、open fd 和异步工作之间的生命周期明确。
- [ ] 测试含并发、signal、nonblock 和失败路径。
