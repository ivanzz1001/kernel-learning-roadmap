# 第 2 章：内核启动、系统调用与源码导航

## 本章目标

用四周建立内核全景图。重点不是背诵启动函数，而是掌握一种能迁移到任何子系统的阅读方法：确认版本、找入口、找核心对象、找状态变化、找并发约束、用动态证据验证。

## 第 5 周：启动主线

### 分层认识启动过程

```text
固件/bootloader
    ↓ 加载压缩内核和 initramfs
架构相关早期代码
    ↓ 建立最早期 CPU、页表和执行环境
解压与架构初始化
    ↓
start_kernel
    ↓ 初始化调度、内存、中断、时钟、VFS 等
rest_init
    ↓
kernel_init → exec init
```

不同架构和版本路径有差异，以上只是导航框架。始终在当前源码中确认符号。

### 源码阅读任务

从 `init/main.c:start_kernel` 出发，为下列问题各找一个证据：

- 中断在什么时候可用？
- 调度器在什么时候初始化？
- slab 分配器何时可用？
- VFS/文件系统初始化从哪里触发？
- 第一个用户态进程如何被选择？
- 内核命令行怎样被解析？

使用：

```bash
rg -n '^asmlinkage __visible void __init start_kernel' init
git log -L :start_kernel:init/main.c --oneline
git blame -L <起始行>,<结束行> init/main.c
```

`git blame` 不是为了找“责任人”，而是为了追到改变设计的 commit message 和讨论背景。

### 动态实验：initcall 时间

在启动参数加入 `initcall_debug`，保存串口日志。找出最慢的 10 个 initcall，回答：它们是否稳定？增加 CPU/减少设备后是否变化？日志时长是否等价于函数真实 CPU 时间？

## 第 6 周：系统调用路径

### 需要区分的四层

1. 用户程序调用 libc wrapper；
2. wrapper 准备 syscall number 和参数；
3. CPU 指令切换到高权限入口；
4. 架构入口保存上下文、分发到通用/具体实现，最后返回。

`getpid()` 可能受 libc/vDSO/缓存策略影响，不要假定每次用户调用都进入内核。可选择 `openat()` 作为更易观察的目标。

### 静态定位方法

```bash
rg -n 'SYSCALL_DEFINE.*\(getpid|openat' .
rg -n '__NR_(getpid|openat)' arch/x86 include
rg -n 'sys_call_table' arch/x86
```

宏会隐藏最终符号。必要时查看预处理结果、构建生成文件和 `nm build/vmlinux`，不要只凭文本搜索认定函数不存在。

### 动态验证

优先选 tracepoint：

```bash
mount -t tracefs nodev /sys/kernel/tracing 2>/dev/null || true
cd /sys/kernel/tracing
echo 0 > tracing_on
echo 1 > events/raw_syscalls/sys_enter/enable
echo 1 > events/raw_syscalls/sys_exit/enable
echo 1 > tracing_on
<运行一个最小测试程序>
echo 0 > tracing_on
cat trace
```

实验结束后关闭事件。生产系统不要无边界启用高频 trace；先在 VM 中限定 PID、事件和持续时间。

### 产出：系统调用证据表

| 层次 | 符号/指令 | 源码/二进制位置 | 验证方法 |
|---|---|---|---|
| 用户 API |  |  | GDB/objdump |
| 架构入口 |  |  | 源码 + 断点 |
| 分发表 |  |  | 生成文件/nm |
| 具体实现 |  |  | ftrace/tracepoint |
| 返回用户态 |  |  | GDB/架构文档 |

## 第 7 周：Kconfig 与 Kbuild

### 核心问题

- Kconfig 决定“是否可选、依赖谁、取 y/m/n 中哪个值”。
- Makefile/Kbuild 决定“哪个对象进入 built-in 或 module、如何组合”。
- `select` 会强制打开目标，可能绕过依赖；新手优先理解 `depends on`。
- `IS_ENABLED(CONFIG_FOO)` 与预处理 `#ifdef CONFIG_FOO` 的行为和用途不同。

### 实验：增加可配置启动特性

在自己创建的学习目录中加入：

1. `config LAB_BOOT_MESSAGE`，类型 bool，默认 n；
2. 对应对象只在该配置启用时构建；
3. initcall 打印一条包含版本标记的日志；
4. 分别构建 `n` 和 `y`，用 `nm` 与启动日志证明差异；
5. 将实现改为 tristate，观察 `m` 需要哪些模块入口变化。

验收不只看“编译通过”：还要验证关闭配置时二进制中没有残留符号。

### 配置可重复性

```bash
scripts/config --file build/.config -e <OPTION>
make O=build olddefconfig
make O=build savedefconfig
scripts/diffconfig old.config build/.config
```

保存精确 `.config`，同时保存生成它的最小 fragment。完整配置便于复现，fragment 便于理解意图。

## 第 8 周：陌生源码阅读法

### 六张地图

面对一个子系统，依次画出：

1. **目录地图**：实现、公共头文件、UAPI、测试、文档在哪里？
2. **入口地图**：系统调用、文件操作、网络事件、驱动 probe、initcall 从哪里进入？
3. **对象地图**：核心结构体之间怎样引用？谁拥有谁？
4. **状态地图**：对象经历哪些状态，谁能改变状态？
5. **并发地图**：进程/中断/软中断上下文，锁顺序，RCU 或引用计数。
6. **观测地图**：tracepoint、统计量、debugfs、日志和测试在哪里？

### 推荐检索顺序

```bash
rg -n '<接口或符号>' Documentation include tools/testing <子系统目录>
git log --oneline --decorate -- <路径>
git log -S'<关键字段或字符串>' -- <路径>
git log -G'<正则>' -- <路径>
git show <commit>
```

- `-S` 找字符串出现次数变化，适合追字段/调用加入或删除。
- `-G` 找 diff 行匹配正则，适合语法模式。
- 阅读 commit 时同时看问题描述、修复策略、Fixes 标签和测试。

### 阶段项目：启动地图

至少包含：

- 从 QEMU 加载到 `/init` 的时间线；
- 15～25 个关键函数及当前源码位置；
- 每个阶段一个可观察日志或断点；
- 一个自己添加的 initcall；
- 一次失败启动（例如 init 缺失）的根因分析；
- “我尚未确认的三件事”。

## 常见误区

- 把架构特定实现当成通用实现。
- 只看函数定义，不看调用上下文和对象生命周期。
- 用旧文章中的函数名强行解释新版本。
- 把调用图工具输出当成真实运行路径；函数指针、宏和条件编译会造成遗漏。
- 修改后只看日志出现，不验证配置关闭、失败路径和回退行为。

## AI 提示词

```text
目标版本是 <commit>，我要理解 <入口> 到 <结果> 的路径。
请只给“检索计划”：候选文件、符号、结构体、配置项、tracepoint 和可能的函数指针分发点。
把可能随架构/配置变化的内容标出来。不要直接声称调用链已成立；为每条边给验证办法。
```
