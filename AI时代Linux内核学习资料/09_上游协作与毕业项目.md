# 第 9 章：上游协作与毕业项目

## 本章目标

完成一个范围明确、可复现、可测试、可审查的内核项目，并将改动整理为符合社区习惯的 patch series。发送邮件不是必选项；形成发送就绪的高质量补丁是最低毕业标准。

## 第 37 周：选择问题

### 好的第一个问题

- 规模小、行为可复现、影响边界明确。
- 位于有测试或容易补测试的子系统。
- 近期仍有维护活动。
- 能解释用户影响，而不是单纯“代码看起来更漂亮”。
- 不依赖无法获得的硬件或私有规格。

适合：真实错误路径修复、测试缺口、文档与当前行为不一致、小型静态检查告警（确认是真问题）。不适合：大规模重构、凭不足基准做核心调度优化、无用户价值的 whitespace/spelling churn。

### 研究维护上下文

```bash
./scripts/get_maintainer.pl -f <target-file>
git log --oneline --decorate -- <target-path>
git log --since='1 year ago' -- <target-path>
git shortlog -sne -- <target-path>
```

阅读 `MAINTAINERS`、子系统文档和近期 patch 讨论。不同子系统有自己的树、测试和提交规则，通用指南不是全部要求。

### 问题陈述模板

```text
在 <版本/配置/环境> 下，当 <输入或状态> 时，<实际行为>。
预期行为是 <可由文档/契约/历史证明>。
用户影响为 <错误、崩溃、性能、可维护性>。
最小复现为 <命令/测试>，复现率 <n/m>。
本项目不处理 <明确边界>。
```

## 第 38 周：设计与拆分 commits

### 推荐 patch series 结构

根据实际问题裁剪：

1. 测试或重现基础设施；
2. 无行为变化的必要准备；
3. 核心修复/功能；
4. 补充测试和文档。

每个 commit 应独立构建，最好独立测试；不要先提交破坏构建的测试再在下一 patch 修复，除非子系统明确接受这种安排。

### commit message 结构

```text
subsystem: concise summary

Describe the observable problem and conditions.
Explain the root cause and relevant invariant.
Explain the change and why this approach is appropriate.
State side effects or tradeoffs.

Tested: <exact test/config/architecture>
Fixes: <commit> ("subject")       # 确实是修复时
Signed-off-by: Your Name <email>  # 只有本人理解并同意 DCO 才签署
```

标题和正文格式以[官方提交指南](https://docs.kernel.org/process/submitting-patches.html)为准。不要让 AI 虚构 `Fixes`、测试结果、性能数据、reviewed-by 或 signed-off-by。

### 自审每个 diff

```bash
git diff --check
git show --stat --oneline HEAD
git show --word-diff HEAD
git range-diff <v1-base>..<v1-tip> <v2-base>..<v2-tip>
```

逐行回答：为什么这行属于当前 commit？如果删掉会怎样？测试覆盖了吗？

## 第 39 周：提交前验证

### 基础检查

按变更范围选择，不是所有小 patch 都需全世界构建：

```bash
./scripts/checkpatch.pl --strict <patch-file>
make O=build W=1 -j"$(nproc)"
make O=build C=1 CHECK=sparse <target>
```

还应考虑：相关 KUnit/kselftest、配置项 `y/m/n`、GCC 与 Clang、32/64 位、endianness 或跨架构构建、sanitizer/lockdep、文档构建、性能基线和 ABI 检查。

`checkpatch` 是提示器，不替代判断；每个保留的 warning 都要能解释。

### 生成补丁

```bash
git format-patch --cover-letter --base=<base-commit> <upstream>..HEAD
./scripts/get_maintainer.pl <patch-files>
```

真正发送前：用文本邮件客户端查看补丁没有被换行/HTML 化，确认收件人、版本号、cover letter、threading 和变更说明。第一次发送可先发给自己或使用子系统建议的测试方式。

## 第 40 周：评审与交付

### 回应评审

- 技术意见逐条回应：接受并说明改变，或给证据解释为何不改。
- 不把“已修改”作为唯一回答，指出 v2 的具体位置。
- 新版本包含完整 commit message，不要求 reviewer 去找旧邮件。
- cover letter 增加 `Changes in v2`，必要时用 range-diff 自审。
- 收到疑问先复现实验，不以 AI 输出代替技术证据。

### 毕业项目四选一

1. **驱动**：QEMU 虚拟设备 + driver + interrupt/DMA 受控实验。
2. **内存/调度**：低开销观测器 + 真实负载分析 + 回归检测。
3. **VFS/网络**：小型功能、bugfix 或测试增强。
4. **质量**：KUnit/kselftest、Coccinelle 规则或 syzkaller description。

### 交付目录

```text
capstone/
├── README.md
├── DESIGN.md
├── REPRODUCE.md
├── SECURITY.md
├── benchmark/
├── tests/
├── configs/
├── logs/
└── patches/
```

### README 必须回答

- 解决什么真实问题，谁会受益？
- 支持哪些 commit/config/architecture？
- 如何从干净环境构建和运行？
- 正常、边界、失败、并发测试是什么？
- 安全边界和需要的特权是什么？
- 性能开销与已知限制是什么？
- 如何完全清理实验资源？

## 毕业答辩自测

不用看材料，在 20 分钟内回答：

1. 从用户操作到你的核心代码，控制流怎样走？
2. 核心对象由谁创建、持有、共享、销毁？
3. 代码会在哪些上下文执行，能否睡眠？
4. 有哪些锁/RCU/refcount，不变量是什么？
5. 三条最危险失败路径是什么？
6. 如何证明修复前失败、修复后通过？
7. 哪些配置或架构未测试？
8. 最可信的反对意见是什么？

如果无法回答，先补实验和文档，不急于发送。

## AI 使用红线

- AI 不得替你添加 `Signed-off-by`、`Tested-by`、`Reviewed-by`。
- 不得声称运行了实际未运行的测试。
- 不得虚构邮件列表共识、maintainer 意见或 commit ID。
- 不把私有漏洞细节发给外部模型；安全问题遵循内核安全报告流程。
- AI 生成的代码必须逐行理解，并由本地构建、测试和工具输出验证。

## 本章验收

- [ ] 问题有稳定复现和用户影响。
- [ ] patch series 每个 commit 单一、可构建、可解释。
- [ ] 测试覆盖正常、边界、失败与并发路径。
- [ ] 提交说明不含虚构标签或测试。
- [ ] 陌生开发者可按文档复现结果。
