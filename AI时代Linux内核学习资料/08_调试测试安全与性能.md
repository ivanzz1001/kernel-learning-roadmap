# 第 8 章：调试、测试、安全检测与性能分析

## 本章目标

面对 panic、oops、UAF、泄漏、死锁、竞态或性能退化时，能够保存现场、提出多个可证伪假设、使用适合的工具缩小范围，并以“修复前失败、修复后通过”的测试证明结果。

## 第 33 周：GDB、日志与 trace

### 调试信息层次

- `dmesg/串口`：时间线、警告、oops、panic。
- dynamic debug/`pr_debug`：局部显式日志。
- tracepoint：较稳定、有结构的事件。
- ftrace function/function_graph：真实函数执行路径，需严格过滤。
- kprobe：动态探测内部符号，受版本与优化影响。
- perf：采样、硬件/软件计数器和调度分析。
- GDB/QEMU：停止执行、断点、寄存器、内存和源码级检查。

工具选择原则：使用能回答当前问题的最低侵入方案。不要一开始全函数跟踪或在高频路径大量 printk。

### QEMU/GDB 实验

QEMU：

```bash
qemu-system-x86_64 -s -S \
  -kernel build/arch/x86/boot/bzImage \
  -initrd rootfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init nokaslr panic=-1" \
  -nographic
```

GDB：

```gdb
file build/vmlinux
target remote :1234
hbreak start_kernel
continue
bt
info locals
ptype struct task_struct
p/x $cr3
```

再对可加载模块使用内核提供的 GDB helper 加载符号。模块地址随加载变化，不能直接复用上次地址。

### oops 初读顺序

1. 保存从第一条 warning/oops 到末尾的完整日志。
2. 异常类型与访问地址：NULL、低地址、已释放 poison、越界特征？
3. CPU、PID、进程、taint、内核版本和 config。
4. faulting instruction 与寄存器。
5. call trace 中第一个可信业务帧，不只看栈顶公共异常处理。
6. 是否有更早的 warning 破坏了状态。
7. 用 `scripts/decode_stacktrace.sh`、`addr2line` 或 GDB 对应到精确构建。

## 第 34 周：测试分层

### KUnit 与 kselftest

- KUnit：内核内部单元/组件测试，适合纯逻辑、解析器、数据结构和可隔离 helper。
- kselftest：从用户态验证内核 ABI、系统调用、sysfs/procfs、设备和端到端行为。
- 两者互补：字符设备的 ring buffer 逻辑可用 KUnit，open/read/poll 接口用 kselftest。

KUnit 最小运行入口：

```bash
./tools/testing/kunit/kunit.py run
```

kselftest 可按 target 构建和运行：

```bash
make -C tools/testing/selftests TARGETS=<target>
make -C tools/testing/selftests TARGETS=<target> run_tests
```

以目标版本官方文档和 Makefile 为准；部分测试需要 root、特定配置或硬件。

### 好测试的性质

- 能在修复前稳定失败。
- 只验证公开契约或明确内部不变量，不绑定无关实现细节。
- 有超时，不会因失败永久挂住。
- 退出码可靠，输出包含上下文。
- 不依赖执行顺序和前次残留。
- 对资源、namespace、模块和临时文件完整清理。

### 测试矩阵

| 维度 | 示例 |
|---|---|
| 配置 | feature y/m/n、debug on/off |
| 输入 | 0、1、边界、超长、无效指针 |
| 并发 | 单线程、多线程、多进程、signal |
| 生命周期 | 重复 open/close、load/unload、创建/删除 |
| 失败 | 分配失败、copy fault、I/O error、timeout |
| 架构 | 32/64 位、不同 endian（可用交叉构建） |

## 第 35 周：检测器与 fuzzing

### 选择工具而非全部开启

| 问题 | 首选工具 | 补充 |
|---|---|---|
| slab/heap 越界、UAF | KASAN | KFENCE、page_owner |
| 未初始化值 | KMSAN | compiler warnings |
| 数据竞争 | KCSAN | lockdep、定向交错 |
| 锁顺序/原子上下文问题 | lockdep/debug atomic sleep | ftrace |
| 泄漏 | kmemleak | 分配计数、引用审计 |
| 覆盖引导 fuzzing | KCOV + syzkaller | 最小化复现 |
| C 语义问题 | UBSAN | 编译器 warning |

组合检测器会进一步改变时序与资源消耗。竞态消失或出现都不能单独证明根因。

### syzkaller 学习目标

第一阶段不是“挖 0day”，而是读懂：

- syz-manager 如何调度 VM 与程序；
- syscall descriptions 如何定义输入空间；
- KCOV 怎样提供覆盖反馈；
- crash 如何保存、去重和最小化；
- reproducer 为什么可能不稳定；
- 报告如何映射到精确 commit/config。

syzkaller 需要隔离 VM、SSH、debugfs、KCOV 和适合的检测器配置，按其[官方 Linux setup](https://github.com/google/syzkaller/blob/master/docs/linux/setup.md)搭建。不要对连接生产网络或含重要数据的机器 fuzz。

### 公开报告复现练习

选择一个已修复、影响较小、环境需求明确的公开报告：

1. 固定报告对应 commit/config。
2. 编译易受影响版本并运行原始 reproducer。
3. 记录复现率，不把一次失败视为不可复现。
4. 阅读修复 commit 前先形成自己的根因假设。
5. 应用修复并运行相同测试。
6. 确认不是配置变化或时序掩盖。

## 第 36 周：性能分析方法

### 正确顺序

```text
定义用户可见指标
  → 固定环境并建立基线
  → 提出瓶颈假设
  → 选择计数器/采样/trace 验证
  → 做最小修改
  → A/B 重测与统计
  → 检查其他指标是否回退
```

### 实验纪律

- 记录 commit、config、编译器和优化选项。
- 固定 CPU topology/affinity/frequency 策略，或记录不可控因素。
- 预热并重复，随机或交替 A/B 顺序以减小漂移。
- 报告样本数、p50/p95/p99、置信范围或方差。
- 同时报告吞吐、延迟、CPU、内存和错误率中的相关指标。
- profile 工具本身会改变系统；测量其开销。

### perf 实验

对一个 CPU-bound 和一个 I/O-bound 负载分别执行：

```bash
perf stat -r 10 <command>
perf record -g -- <command>
perf report
```

解释 cycles/instructions/IPC、context switches、faults 对两类负载意味着什么，以及它们不能证明什么。虚拟机中的硬件计数器可能受限，需检查 `perf stat` 是否显示 unsupported/not counted。

## 阶段项目：五类故障档案

每类一个独立目录：

```text
fault-case/
├── README.md
├── trigger/
├── logs/
├── analysis.md
├── fix.patch
└── regression/
```

五类：panic/oops、越界或 UAF、泄漏/引用未释放、deadlock 或 data race、性能退化。

### 每份分析必须回答

- 首个异常事件是什么？
- 哪些是事实，哪些是推断？
- 至少两个候选根因如何被排除？
- 根因对应的对象生命周期或不变量是什么？
- 为什么补丁修复根因而不是隐藏症状？
- 哪个测试能防止复发？
