# 第 1 章：C、ELF 与 Linux 系统编程

## 本章目标

这四周不追求掌握所有 C 语法，而是掌握内核开发真正依赖的能力：精确理解对象布局和生命周期、识别未定义行为、读懂编译链接结果、正确处理系统调用的失败与部分完成。

## 第 1 周：对象、指针与内存

### 概念地图

- **对象与存储期**：automatic、static、allocated、thread-local。
- **值与表示**：有符号溢出、大小端、对齐、padding、strict aliasing。
- **指针**：指向对象、越界规则、函数指针、`void *`、`const` 的位置。
- **结构体**：布局受 ABI 与对齐影响，不能凭字段大小相加猜测 `sizeof`。
- **宏**：参数可能求值多次；多语句宏需要安全包裹；类型检查弱。
- **生命周期**：拥有者、借用者、引用计数、释放后引用。

### 实验 1：结构体与容器

定义一个包含 `char`、`int`、指针和嵌套结构体的类型，打印每个字段 `offsetof`、结构体 `sizeof` 和 `_Alignof`。改变字段顺序，对比大小；使用 `pahole` 观察空洞。

思考：内核为何经常通过重新排列字段减少 cache footprint？为什么 ABI 结构体不能随意调整？

### 实验 2：实现简化版侵入式链表

不要把数据复制进链表节点，而是在业务对象内嵌 `list_node`，再用 `offsetof` 从成员指针反推容器地址。随后阅读 `include/linux/list.h` 中的 `container_of` 和 list API，比较你的实现遗漏了哪些类型检查与边界处理。

### 实验 3：让工具发现错误

分别制造：heap buffer overflow、use-after-free、double free、signed overflow、data race。用户态用以下组合构建：

```bash
cc -O1 -g -Wall -Wextra -Werror \
  -fsanitize=address,undefined demo.c -o demo
```

数据竞争单独使用 ThreadSanitizer：

```bash
cc -O1 -g -fsanitize=thread -pthread race.c -o race
```

记录检测器报告的第一处错误、分配栈、访问栈，而不是只保存最后一行。

## 第 2 周：从 C 到 ELF

### 编译流水线

```text
源代码 → 预处理结果 → 汇编代码 → 可重定位目标文件 → ELF 可执行文件/共享库
```

你需要能回答：某个符号在哪里定义、何时解析、最终位于哪个 section、运行地址由谁决定。

### 必会工具

```bash
cc -E demo.c -o demo.i
cc -S -O2 -g demo.c -o demo.s
cc -c -O2 -g demo.c -o demo.o
readelf -hSWs demo.o
nm -n demo.o
objdump -drS demo.o
```

- `readelf -S`：section 表。
- `readelf -s`/`nm`：符号绑定、可见性、是否未定义。
- `objdump -drS`：源码、汇编和重定位交叉观察。
- `ldd`：动态依赖；不要对不可信文件直接执行它。

### 实验：追踪一个外部函数

写 `main.c` 调用另一个目标文件中的 `add()`：

1. 在 `main.o` 中找 `add` 的未定义符号与重定位项。
2. 链接后确认符号地址。
3. 加 `static` 后观察可见性变化。
4. 使用共享库再做一次，对比 PLT/GOT。
5. 用 GDB 的 `disassemble /m`、`info address`、`x/i` 核对。

## 第 3 周：进程、文件描述符与虚拟内存

### 进程闭环

- `fork()` 复制的是进程执行上下文视图，物理页通常借助 COW 延后复制。
- `execve()` 替换当前进程映像，不创建新进程。
- `waitpid()` 回收子进程退出状态，避免 zombie。
- 文件描述符是进程表中的索引；dup 后多个 fd 可指向同一个 open file description。

每个 syscall 都可能失败。用户态代码至少处理：返回值、`errno`、`EINTR`、部分读写、资源回收。

### 实验 1：fork/exec/wait

父进程创建管道，fork 后子进程把 stdout 重定向到管道并 exec `/bin/uname`，父进程读取输出并 wait。验证以下错误路径：exec 文件不存在、父进程提前关闭、read 被 signal 中断。

### 实验 2：COW

1. `mmap` 一块较大匿名内存并逐页写入。
2. 记录 `/proc/self/stat` 或 `getrusage` 的 minor faults。
3. fork 后仅由子进程写一半页面。
4. 比较父子 RSS/PSS、minor fault 变化。
5. 用 `perf stat -e page-faults,minor-faults,major-faults` 复核。

不要用一次测量下结论；预热、重复并记录页大小、THP 状态和负载。

### 实验 3：文件映射

比较 `read/write` 与 `mmap` 修改文件：什么时候内存变化可见？`msync`、`fsync` 各保证什么？异常退出时哪些假设不成立？本实验只对临时文件执行。

## 第 4 周：综合项目 mini shell

### 最小需求

- 解析命令与参数；明确说明不支持完整 shell quoting 也可以。
- fork + exec 启动程序。
- 支持一个管道和 `>` 重定向。
- 正确关闭所有无用 pipe fd，否则 EOF 可能永远不到来。
- `SIGINT` 不应直接杀死 shell 本身；前台子进程应能收到信号。
- 回收所有子进程并报告退出码。
- 对系统调用错误给出包含 `errno` 的信息。

### 测试清单

```text
普通命令：       echo hello
参数：           printf '%s\n' a b
重定向：         echo hello > /tmp/out
管道：           printf 'b\na\n' | sort
不存在的程序：   no-such-command
被信号终止：     启动 sleep 后发送 Ctrl-C
压力：           连续执行 1000 个短命令并检查 zombie
```

### Git bisect 练习

在项目历史中人为建立 8～10 个小提交，其中一个引入可自动检测的错误。编写退出码明确的测试脚本，执行：

```bash
git bisect start
git bisect bad
git bisect good <已知正常提交>
git bisect run ./tests/regression.sh
git bisect reset
```

解释为什么不稳定测试会使 bisect 结果失真。

## 源码衔接

完成用户态实验后，在内核源码中定位相应概念：

| 用户态概念 | 内核源码入口（以当前版本核对） |
|---|---|
| 进程描述 | `include/linux/sched.h` 中的 `task_struct` |
| fork/clone | `kernel/fork.c` |
| exec | `fs/exec.c` |
| wait | `kernel/exit.c` |
| mmap/VMA | `mm/mmap.c`、`include/linux/mm_types.h` |
| fd/file | `fs/file.c`、`include/linux/fs.h` |

不要在这一阶段深入所有实现。任务是建立“用户 API → 内核目录 → 核心对象”的索引。

## AI 协作练习

把一段反汇编交给 AI 时要求：

```text
请按目标 ABI 解释参数、返回值、栈帧和每条内存访问。
把确定事实与推测分开；给出可用 GDB 命令验证每项推测。
不要根据函数名臆测代码语义。
```

随后亲自用 GDB 核验至少三项。如果 AI 给出的寄存器约定、优化行为或符号位置与本机不符，以编译器输出为准，并记录差异原因。

## 本章验收题

1. `sizeof(pointer)` 为什么不能反映指向对象大小？
2. `volatile` 为什么不能替代线程同步或内核锁？
3. `fork` 后为什么某些页面直到写入才产生额外物理占用？
4. 为什么 `read(fd, buf, n)` 成功也可能返回小于 `n`？
5. 一个进程 exec 后 PID 为什么不变？哪些 fd 会保留？
6. ELF 中 section 与运行时 segment 有什么区别？
