# 第 4 章：调度、并发、中断与 RCU

## 本章目标

能够回答内核并发问题最重要的四个问题：代码运行在什么上下文、能否睡眠、状态由谁并发访问、对象什么时候仍然有效。最终完成一份调度延迟实验和一次有证据的死锁修复。

## 第 14 周：任务状态与唤醒

### 不要把“进程状态”当标签背诵

围绕事件理解：任务为什么停止运行、谁改变条件、谁将它放回可运行队列、何时真正获得 CPU。

典型等待闭环：

```text
检查条件 → 条件不满足 → 把任务加入等待结构 → 改变状态并调度出去
条件生产者更新状态 → 唤醒 → 任务进入 runnable → 调度器选中 → 再检查条件
```

条件必须重新检查，因为唤醒不等于条件仍成立，也不等于立刻运行。

### trace 实验

启用并过滤以下调度事件（具体名称以目标内核 `available_events` 为准）：

- `sched:sched_wakeup`
- `sched:sched_waking`
- `sched:sched_switch`
- `sched:sched_process_fork/exec/exit`

写一个周期性睡眠的用户程序，以 PID 过滤 trace，计算 wakeup 到首次被调度的延迟。确认 CPU 迁移时如何关联同一个任务。

## 第 15 周：调度实验方法

### 变量控制

依次只改变一个变量：

- CPU 数量：1、2、4；
- affinity：固定单核与允许迁移；
- nice/调度策略；
- 竞争负载数量；
- 内核抢占配置；
- VM 是否启用硬件加速。

每组至少预热并重复，报告 p50/p95/p99/max 与样本数。QEMU 宿主调度会引入噪声，因此结论应明确限定“此实验环境下”。

### 不应直接下的结论

- 一次 max 很大不等于调度器有 bug。
- `perf` 显示热点不等于优化它必然改善端到端延迟。
- runnable 任务多不等于 CPU 一定饱和。
- 虚拟机中的 steal/宿主抢占可能伪装成客体延迟。

## 第 16 周：执行上下文

### 上下文能力表

| 上下文 | 是否可睡眠 | 常见来源 | 适合工作 |
|---|---|---|---|
| 进程上下文 | 通常可以，取决于持锁/禁抢占状态 | syscall、内核线程 | 可能阻塞的完整处理 |
| hardirq | 不可以 | 设备中断 | 最短确认与状态采集 |
| softirq | 不可以 | 网络、timer 等延后工作 | 有限的原子上下文处理 |
| workqueue | 可以 | worker thread | 从原子上下文移出的慢工作 |
| timer/hrtimer callback | 不可随意睡眠 | 时钟回调 | 更新状态、排队工作 |

“进程上下文”也不自动代表可睡眠：持有 spinlock、关闭中断或处于原子区时仍不能睡眠。

### 实验：hrtimer + workqueue

1. hrtimer 周期触发，只记录时间戳并 queue work。
2. work function 完成可能睡眠的处理。
3. 模块退出顺序：停止新 timer、同步取消、flush/cancel work、释放对象。
4. 故意交换退出顺序，观察潜在 UAF；仅在 KASAN VM 中执行。

为 timer callback 和 work function 记录 PID、CPU、`in_interrupt()` 等上下文信号，解释差异。

## 第 17 周：锁、lockdep 与内存顺序

### 选择同步原语

- mutex：进程上下文互斥，等待者可以睡眠。
- spinlock：原子上下文或极短临界区；持有时不能睡眠。
- rwsem/rwlock：不要只因“读多写少”就选择，先测量争用和公平性需求。
- completion：一次事件完成通知。
- wait queue：围绕条件等待。
- atomic/refcount：只保证特定原子操作，不自动保护复合不变量。
- seqlock：读者可重试，适合小型一致快照，不适合含指针生命周期的任意对象。

### 锁设计步骤

1. 写出共享状态不变量。
2. 列出所有访问上下文。
3. 指定哪个锁保护哪些字段。
4. 若需多锁，建立全局顺序。
5. 检查锁内是否可能 sleep、copy user、分配或调用未知 callback。
6. 使用 lockdep 验证，但不把“没有报告”当作完整证明。

### lockdep 实验

线程 A 获取 L1 再 L2，线程 B 获取 L2 再 L1。通过 completion 控制交错，稳定触发 lockdep 的 circular dependency 报告。修复后解释：是统一锁顺序、合并锁还是改变数据结构？修复如何被测试覆盖？

### 内存屏障学习边界

先通过锁、RCU 和现成原语表达同步。若确实阅读 lock-free 代码，逐一回答：

- 哪个 load 与哪个 store 建立顺序？
- 哪个 CPU/设备是观察者？
- 使用 acquire/release 还是更强屏障？
- 数据依赖、编译器重排和 CPU 重排分别受什么限制？
- litmus test 能否表达预期？

不要让 AI 凭直觉补 `smp_mb()`；屏障必须有成对关系和注释。

## 第 18 周：RCU 与生命周期

### RCU 的核心模型

RCU 适用于读多写少：读者低开销访问旧/新版本之一，更新者发布新状态，等待旧读者离开 grace period 后回收旧对象。RCU 解决的是访问与回收协调，不自动让复合更新具备事务一致性。

### 阅读任务

在一个使用 RCU 的小型内核数据结构中识别：

- reader critical section；
- dereference/publish primitive；
- updater serialization；
- grace period；
- deferred free；
- 与引用计数或锁的配合。

### 实验：读多写少配置表

先用 rwlock 实现一个小表，再改成 RCU：

- 多个内核线程反复读取；
- 单个更新线程替换对象；
- 对象包含 generation，读者检查内部一致性；
- KASAN 下压力运行；
- 比较吞吐，同时说明基准局限。

## 阶段项目：调度延迟报告

报告结构：

1. 问题：某类任务从 wakeup 到执行的延迟受哪些因素影响？
2. 环境：commit、config、QEMU/硬件、CPU topology、负载。
3. 事件：如何关联 wakeup/switch，如何处理迁移和丢事件。
4. 实验矩阵：每次只改变一个变量。
5. 结果：直方图、p50/p95/p99/max、样本数。
6. 异常样本：回看前后事件，不删“难看数据”。
7. 结论：事实、推断、限制分开。

## 常见误区

- 认为 spinlock 一定比 mutex 快。
- 认为 atomic 变量周围的所有访问都自动有序。
- 认为唤醒后任务立即运行。
- 在 timer/interrupt 中调用可能睡眠的 API。
- cancel 异步工作后未等待正在执行的 callback 退出。
- 释放对象前没有阻止新读者或等待旧读者离开。
