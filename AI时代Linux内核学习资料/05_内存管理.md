# 第 5 章：Linux 内存管理

## 本章目标

从一次地址访问出发，理解 VMA、页表、缺页、物理页分配、slab、页缓存、回收和 OOM 的关系；能够通过 `/proc`、tracepoint、perf 和内存检测器建立证据链。

## 第 19 周：虚拟地址、VMA 与缺页

### 地址访问的层次

```text
进程虚拟地址
  → VMA：该范围是否合法、权限和后端是什么
  → 页表：是否已有映射、权限是否允许
  → TLB：CPU 是否缓存了翻译
  → 物理页或设备映射
```

缺页不是天然错误。按需分配、文件页首次访问和 COW 都通过 page fault 完成；非法地址或权限冲突才会导致信号/异常。

### 需要区分

- minor fault：通常无需从存储设备读取，但仍可能分配页或建立映射。
- major fault：处理需要 I/O；其定义和计数语义应以当前文档/实现为准。
- anonymous vs file-backed。
- private vs shared mapping。
- 虚拟空间大小 vs RSS vs PSS。

### 实验：受控缺页

写程序接受 `size`、访问步长、读/写模式：

1. `mmap` 但不触碰，记录 VIRT/RSS/fault。
2. 每页读一次。
3. 每页写一次。
4. `fork` 后子进程写一半页面，观察 COW。
5. 文件映射冷/热缓存各测一次。

采集：

```bash
perf stat -e page-faults,minor-faults,major-faults ./fault-lab
cat /proc/<pid>/maps
cat /proc/<pid>/smaps
cat /proc/vmstat
```

清空系统 page cache 会影响全机，且需要特权；不应在共享/生产系统执行。使用新文件、受控 VM 或不同文件偏移构造冷读。

## 第 20 周：物理页、buddy 与 slab

### 分配器分工

- buddy/page allocator：以页和 order 为单位提供物理页块。
- SLUB/其他 slab allocator：从页中切分频繁使用的小对象并缓存。
- `kmalloc`：物理上适合 DMA/连续性语义的常见小分配接口，限制随 size/order 和上下文变化。
- `vmalloc`：虚拟连续，物理页不必连续；映射与访问开销不同。
- mempool：在必须进展的路径中预留元素，不是无限内存。

### GFP 不是“随便选的标志”

选择 GFP mask 前回答：当前上下文能否睡眠？允许直接回收或 I/O 吗？是否处于文件系统/块层递归路径？是否必须从特定 zone/节点？优先使用子系统惯例和封装 API。

### 实验：分配行为

在 QEMU 中：

1. 读取 `/proc/buddyinfo`、`/proc/slabinfo`、`/proc/meminfo` 基线。
2. 模块分配大量固定小对象，观察对应 slab/cache。
3. 释放一半与全部，观察缓存不会必然立刻归还所有页。
4. 比较 `kmalloc` 与 `vmalloc` 返回地址、最大可用大小和失败行为。
5. 不断增加高 order 分配，观察碎片与失败；设置硬上限，避免 VM 无响应。

不要把“free 后 MemFree 没恢复”直接判断为泄漏；slab/page cache 可能保留可回收内存。

## 第 21 周：页缓存、回收和 swap

### 回收问题链

内存紧张时，需要判断：

- 哪些页可直接丢弃或回写后回收？
- 匿名页是否可 swap？
- 当前 cgroup/NUMA/zone 是否局部受限？
- 分配 order 和 GFP mask 是否让“总内存尚有空闲”仍然失败？
- direct reclaim、kswapd 和 compaction 各在做什么？

### 实验：memory pressure

在限制为 2 GiB 的 VM 或单独 memory cgroup 中，逐步申请并触碰匿名内存。采集：

- `/proc/meminfo`、`/proc/vmstat` 差分；
- PSI memory；
- major/minor faults；
- swap in/out；
- reclaim/compaction tracepoints；
- 测试进程延迟分位数。

实验矩阵：有/无 swap、匿名/文件负载、不同工作集大小。每轮恢复快照或等待环境稳定。

### 页缓存实验

读取一个大于可用内存的临时文件，观察 cache 与 reclaim。随后用同尺寸匿名内存竞争。解释为什么应用 RSS、cache、slab 简单相加可能重复或误导。

## 第 22 周：OOM 与 cgroup

### OOM 分析顺序

1. 确认是全局 OOM、memory cgroup OOM 还是特定 NUMA/zone 约束。
2. 看触发分配的 order、GFP mask 和调用栈。
3. 看允许的 nodes/cpuset、cgroup limit、swap 配置。
4. 看候选任务内存、`oom_score_adj` 和选中结果。
5. 解释“谁触发”不一定等于“谁消耗最多”或“谁被杀”。

### 安全实验

只在 VM 内，将一个测试程序放进有限 memory cgroup。让它按固定速率申请并触碰内存，保存串口日志。分别设置：

- cgroup limit 低于 VM 总内存；
- 有/无 swap；
- 两个进程不同 `oom_score_adj`（仅实验环境）；
- 文件缓存与匿名内存组合。

产出完整 OOM 日志注释：每个关键字段的含义、约束来源、被杀原因和不确定点。

## 第 23 周：内存错误检测

### 工具选择

| 工具 | 主要发现 | 代价/注意事项 |
|---|---|---|
| KASAN | 越界、UAF 等内存访问错误 | 内存和性能开销大 |
| KFENCE | 低频采样式堆错误 | 开销较低，不保证每次捕获 |
| KMSAN | 未初始化值传播 | 构建和运行要求较高 |
| kmemleak | 疑似内核内存泄漏 | 可有误报/不可见分配 |
| UBSAN | 部分未定义行为 | 需结合具体报告判断 |
| page_owner | 页分配来源 | 有存储与运行开销 |

### 故障实验

学习模块中分别制造：

- heap out-of-bounds；
- use-after-free；
- 忘记释放的对象；
- double free（可能立即破坏系统，只在可丢弃 VM）；
- 错误引用计数。

每个故障保存：触发代码、配置、完整报告、第一处异常访问、分配栈、释放栈、根因、修复和回归测试。

## 阶段项目：缺页与回收观测器

### 最低功能

- 输入 PID 或 cgroup。
- 按时间窗口输出 minor/major fault、reclaim stall、swap、RSS/anon/file 变化。
- 用直方图或分位数显示停顿，不能只输出累计次数。
- 提供两个负载：匿名随机访问、文件顺序/随机访问。
- 标记丢事件、采样偏差和需要的权限/配置。

### 推荐实现层次

1. 先用 `/proc` + `perf stat` 建立正确性基线。
2. 再用 tracefs/tracepoint 获得事件时间线。
3. 第 7 章学完后可改用 BPF 聚合，比较开销和可部署性。
