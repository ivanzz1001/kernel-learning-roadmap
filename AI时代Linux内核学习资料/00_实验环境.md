# 第 0 章：搭建可重复的内核实验环境

## 本章目标

完成本章后，你应能从固定源码版本构建内核，在 QEMU 中进入 BusyBox shell，通过串口保留日志，并用 GDB 连接到暂停的虚拟机。

## 为什么使用 QEMU

内核错误可能导致宿主机重启、文件系统损坏或网络中断。QEMU 提供可丢弃磁盘、快照、串口日志和 GDB stub，适合反复制造 panic、UAF、死锁和 OOM。虚拟机不是绝对安全边界，因此仍应：使用非特权用户、禁用不必要网络、不给客体挂载重要宿主目录。

## 版本策略

- 实验版本固定为一个仍受支持的 LTS **精确标签**，例如 `v6.x.y`，不要只写“最新版本”。
- `notes/environment.md` 记录源码 commit、编译器、binutils、QEMU、BusyBox、`.config` 哈希和启动参数。
- 每月可以另建分支对照主线；不要悄悄升级实验底座。
- 活跃 LTS 状态随时间变化，以 [kernel.org releases](https://www.kernel.org/releases.html) 为准。

## 主机依赖

Debian/Ubuntu 名称示例：

```bash
sudo apt update
sudo apt install git build-essential bc bison flex libssl-dev \
  libelf-dev libncurses-dev dwarves cpio qemu-system-x86 gdb \
  clang llvm lld rsync
```

不同发行版包名可能不同。缺失头文件时先读构建错误，确认它属于主机工具、开发头文件还是内核配置，不要一次性安装来源不明的依赖集合。

## 获取并固定源码

```bash
mkdir -p kernel-lab
cd kernel-lab
git clone https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git
cd linux
git tag -l 'v6.*' | tail
git checkout <精确-LTS-标签>
git rev-parse HEAD
```

学习最新合入过程时可另取主线：

```bash
git remote add torvalds https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
git fetch torvalds master
```

## 第一次构建

始终使用 out-of-tree 构建：

```bash
mkdir -p ../build
make O=../build x86_64_defconfig
make O=../build menuconfig
make O=../build -j"$(nproc)"
```

建议调试配置：

```text
CONFIG_DEBUG_INFO=y
CONFIG_GDB_SCRIPTS=y
CONFIG_FRAME_POINTER=y
CONFIG_KALLSYMS=y
CONFIG_KALLSYMS_ALL=y
CONFIG_DEBUG_FS=y
CONFIG_TRACE_FS=y
CONFIG_FTRACE=y
CONFIG_FUNCTION_TRACER=y
CONFIG_KPROBES=y
```

调试初期追加启动参数 `nokaslr`，使运行地址与符号稳定。安全检测器会显著增加内存与编译时间，应在对应章节按需开启，不必第 0 周全部启用。

## 构建最小 BusyBox initramfs

先取得并静态编译 BusyBox：

```bash
git clone https://git.busybox.net/busybox ../busybox
make -C ../busybox defconfig
make -C ../busybox menuconfig
make -C ../busybox -j"$(nproc)"
make -C ../busybox CONFIG_PREFIX="$PWD/../rootfs" install
```

在 menuconfig 中启用 `Settings → Build static binary`。根文件系统至少包含：

```text
rootfs/
├── bin/busybox
├── dev/
├── proc/
├── sys/
├── tmp/
└── init
```

`init` 逻辑应完成伪文件系统挂载并进入 shell：

```sh
#!/bin/sh
mount -t proc none /proc
mount -t sysfs none /sys
mount -t devtmpfs none /dev 2>/dev/null
mount -t debugfs none /sys/kernel/debug 2>/dev/null
mount -t tracefs none /sys/kernel/tracing 2>/dev/null
echo "kernel lab is ready"
exec /bin/sh
```

为 `init` 增加可执行权限后打包：

```bash
cd ../rootfs
find . -print0 | cpio --null -ov --format=newc | gzip -9 > ../rootfs.cpio.gz
```

## QEMU 启动与退出

```bash
qemu-system-x86_64 \
  -m 2G -smp 2 -nographic \
  -kernel build/arch/x86/boot/bzImage \
  -initrd rootfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init nokaslr panic=-1"
```

- `-nographic`：串口接管当前终端。
- `console=ttyS0`：把内核日志送到串口。
- `rdinit=/init`：指定 initramfs 的第一个用户进程。
- `panic=-1`：panic 后不自动重启，便于保留现场。
- 退出 QEMU：通常使用 `Ctrl-a x`。

## GDB 调试

调试启动命令增加 `-s -S`：

```bash
qemu-system-x86_64 -s -S \
  -m 2G -smp 2 -nographic \
  -kernel build/arch/x86/boot/bzImage \
  -initrd rootfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init nokaslr panic=-1"
```

另开终端：

```bash
cd kernel-lab/build
gdb vmlinux
```

GDB 中执行：

```gdb
target remote :1234
hbreak start_kernel
continue
bt
info registers
list
```

QEMU 官方文档说明 `-s` 默认监听 1234 端口，`-S` 让客体在 GDB 连接前暂停。不要把 GDB 端口暴露到不可信网络。

## 自动化脚本应具备什么

建议自己编写而不是复制完整脚本。最低要求：

- `build.sh`：检查源码/输出路径、打印 commit、失败即退出。
- `mkrootfs.sh`：每次从明确输入生成 initramfs，不依赖手工残留。
- `run.sh`：统一 CPU、内存、启动参数、日志输出位置。
- `debug.sh`：只比 `run.sh` 多 GDB 相关参数。
- `clean-lab.sh`：只清理明确的构建输出，禁止对宽泛路径执行递归删除。

## 必做实验

### 实验 A：证明运行的是自己的内核

1. 为内核设置 `CONFIG_LOCALVERSION="-lab01"`。
2. 编译、启动，记录 `uname -a`。
3. 修改 `init/main.c` 中一处启动日志，重新构建并确认日志出现。
4. 回退修改，确认日志消失。

### 实验 B：建立配置差异意识

```bash
cp build/.config experiments/config-before
scripts/config --file build/.config -e DEBUG_INFO -e GDB_SCRIPTS
make O=build olddefconfig
cp build/.config experiments/config-after
scripts/diffconfig experiments/config-before experiments/config-after
```

回答：你显式启用的选项是否拉入了其他依赖？为什么？

### 实验 C：第一次源码断点

在 `start_kernel`、`rest_init` 各停一次，记录：当前 CPU、调用栈、一个局部或全局变量。若符号或源码路径不正确，检查是否使用了与 `bzImage` 同一次构建生成的 `vmlinux`。

## 常见故障排查

| 症状 | 优先检查 |
|---|---|
| `No working init found` | `/init` 是否存在、可执行、解释器是否存在、BusyBox 是否静态链接 |
| 没有串口输出 | `-nographic` 与 `console=ttyS0` |
| GDB 断点地址异常 | 是否加载正确 `vmlinux`，是否关闭 KASLR，构建是否含 debug info |
| rootfs 命令缺失 | BusyBox applet 是否安装、`/bin/sh` 链接是否生成 |
| 内核挂载 proc/sys 失败 | 对应文件系统是否启用、目录是否存在 |
| 编译结果污染源码树 | 是否所有 make 命令都一致使用 `O=` |
